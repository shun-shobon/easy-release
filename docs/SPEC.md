# リリース仕様

easy-release は1リポジトリにつき1つの安定版 `X.Y.Z` を管理します。個別パッケージの独立したバージョンやプレリリースは扱いません。

このリポジトリ自身も `Release` ワークフローでリリースします。手動実行で更新種別を選ぶと準備 PR を作成し、マージ後にドラフトを作成して公開します。Action の配布物はタグに含めた `action.yml` と `dist/index.mjs` です。

バージョン入力は正規の表記をそのまま受け付けます。`v` の接頭辞、前後の空白、先頭ゼロ、プレリリース識別子、ビルドメタデータを含む値は補正せず拒否します。

## 設定

設定ファイルは JSON です。全モードで `config` 入力（既定値 `.github/easy-release.json`）から読み込みます。未定義のキーは入力ミスとして拒否します。ファイルの欠落・不正な JSON・設定値の検証失敗では公開前に停止します。

| キー                | 必須 / 既定値      | 意味                                                    |
| ------------------- | ------------------ | ------------------------------------------------------- |
| `packageFiles`      | 必須               | 更新対象を指定する正の glob 配列。コマンドのみなら `[]` |
| `tagPrefix`         | `v`                | リリースタグの接頭辞。空文字も指定可                    |
| `updateVersionTags` | `false`            | 公開成功後にメジャー・マイナータグを両方更新する真偽値  |
| `branchPrefix`      | `release/prepare-` | 準備ブランチの接頭辞。この後にタグ全体を付加            |
| `updateCommand`     | 省略時は実行なし   | パッケージ更新後に実行する Bash コマンド                |

パスはリポジトリルートを基準とします。更新対象の絶対パス、親ディレクトリ参照、シンボリックリンク、`node_modules` と `.git` 内のファイルは認めません。指定されたファイルだけを対象にし、重複は除きます。すべての対象が有効な JSON と安定版の `version` を持つことを検証してから書き込みます。既存の版は計算に使わず、対象間で異なっていても計算後の共通版に揃えます。整形では既存インデント・改行を保持し、その他の JSON 表現は再シリアライズされます。

## バージョンの決定

GitHub API からリポジトリ全体の Git タグを全ページ取得し、`tagPrefix` を除いた名前が正規の安定版 `X.Y.Z` であるものを選びます。SemVer で最大の版を現在版とし、タグの作成日時・一覧の順序・ブランチへの到達可否・リリースの公開状態では絞り込みません。プレリリースやビルドメタデータ付きのタグ、無関係なタグは対象外です。

該当タグがなければ `0.0.0` を基準とし、初回の patch / minor / major はそれぞれ `0.0.1` / `0.1.0` / `1.0.0` になります。タグ一覧の取得失敗では初回扱いにせず停止します。`packageFiles: []` ではパッケージを更新せず、更新コマンドで任意のファイルを変更できます。

更新後に Git の差分がなくても、ベースコミットと同じツリーを持つ空コミットで準備 PR を作成します。パッケージがすでに予定版の場合や、`packageFiles: []` で更新コマンドを指定しない場合も対象です。対象バージョンの検証や更新コマンドの失敗条件は、差分の有無にかかわらず適用します。

## 準備 PR

Action のログ・エラー、生成する PR のタイトル・本文、準備コミットのメッセージは英語で記述します。

ベースブランチはイベントの `repository.default_branch` から取得します。prepare はそのデフォルトブランチの `workflow_dispatch` に限ります。checkout の HEAD とイベント SHA、リモートのベースブランチ先端が一致し、作業ツリーが clean であることが条件です。major は下2桁を0、minor は patch を0にし、patch は末尾を1増やします。各数値は JavaScript の安全な整数の範囲に制限します。

更新コマンドはタグから決定した `PREVIOUS_VERSION` と更新後の `RELEASE_VERSION` を受け取ります。更新コマンド固有の制限時間は設けません。異常終了・64 MiB の出力上限超過・対象バージョンの書き戻しや削除で失敗します。コマンドの異常終了時は起動したプロセスグループを停止します。コマンドが変更したファイルは Git の追跡・無視ルールに従って収集します。バイナリ・ファイル削除・実行属性を保持し、submodule の変更は拒否します。

ブランチ名とタグ名は Git の参照名として検証してからリモートを変更します。GitHub 上に変更コミットを作成した後、同一リポジトリ・同じベースブランチの open PR のうち、設定した接頭辞と厳密なバージョンに一致するものを閉じ、そのブランチを削除します。新しい準備ブランチと PR を作成します。既存のリリースタグは上書きしません。PR のない同名ブランチは、先端のコミットメッセージが同じ版の準備メッセージと完全一致するときだけ、前回の途中状態として削除・再作成します。それ以外の同名ブランチは拒否します。接頭辞はこの Action 専用とします。API の一連の操作はトランザクションではなく、失敗した地点までの状態が残ります。

## ドラフトと公開

draft と、`release-id`・`tag`・`commit` をすべて省略した publish は、`pull_request` の `closed` を受け取ります。マージ済み・同一リポジトリ・リポジトリのデフォルトブランチ・準備ブランチ名の4条件に合わない PR は `ready: false` とします。条件に合う PR では、checkout がマージコミットであることを検証し、準備ブランチ名からリリース予定版を取得します。glob を再展開し、マージ時点の全対象パッケージがその版であることを検証します。この段階ではタグから増分を再計算しません。

リリースタグはマージコミットに作成します。既存タグは参照先を検証し、異なるコミットなら失敗します。リリースは `draft: true` と GitHub の自動生成ノートで作成します。同じタグ・コミットのドラフトは再利用します。公開済みのものは拒否します。

prepare → publish では、準備 PR のマージコミットを checkout し、`mode: publish` を実行します。版・checkout・対象パッケージの検証、タグとドラフトの作成または再利用、公開条件の検証、公開を1回の呼び出しで行います。成功時は `ready: true`、`version`、`tag`、`commit`、`release-id`、`release-url` を出力します。対象外の PR では `ready: false` のみを出力します。途中で失敗した場合は停止し、作成済みのタグやドラフトは残ります。同じタグ・コミットのドラフトから再実行できますが、公開済みリリースは拒否します。

既存ドラフトの公開では `release-id`・`tag`・`commit` をすべて指定します。一部だけの指定は入力エラーとし、PR イベントからの公開には切り替えません。この形式でも設定ファイルを読み込むため checkout が必要ですが、PR イベントとパッケージの検証は行いません。

利用側 workflow がビルドとアセットの添付を実行します。publish は指定した ID のリリースがドラフトであり、タグ・対象コミットが一致し、添付済みアセットがすべて `uploaded` であることを確認して `draft: false` / `make_latest: true` に更新します。必要なアセットの種類や個数は Action では推測しません。同一ジョブでは必要なステップの後に publish を置き、複数ジョブではすべての必要ジョブを `needs` に指定してください。アセット0件のリリースにも対応します。

### メジャー・マイナータグ

draft の有無にかかわらず、設定の `updateVersionTags` が `true` の場合は、公開成功を確認した後にメジャー、マイナーの順でタグを更新します。`v1.2.3` なら `v1` と `v1.2` が対象となり、存在すれば参照を強制更新し、なければ軽量タグを作成します。既存の注釈付きタグも参照を対象コミットへ付け替えます。完全なバージョンのタグは変更しません。prepare / draft ではこのオプションによる更新を行いません。

接頭辞には設定ファイルの `tagPrefix` を使います。有効時は API 呼び出し前に、リリースタグが指定した接頭辞と正規の安定版 `X.Y.Z` で構成されていることを検証します。`app/1.2.3` と接頭辞 `app/` なら `app/1` と `app/1.2` を更新します。`v0.2.3` なら `v0` と `v0.2` を更新します。

タグは今回公開したコミットを指します。既存タグの版との大小比較は行わず、古い版を公開した場合も移動します。メジャー・マイナータグは完全な安定版ではないため、次回 prepare の現在版の計算には含まれません。

リリース公開と各タグ更新はトランザクションではありません。タグの取得・作成・更新で失敗した場合は停止し、公開済みリリースと更新済みタグは残します。自動で再試行やロールバックは行いません。公開済みリリースへの publish 再実行は拒否されるため、未完了のタグ更新は手動で行います。

## 実行環境と外部通信

コミット識別子の入力は空でない文字列として受け付け、桁数や文字種は検証しません。未マージのイベントではマージコミットの `null` を許容します。checkout・タグ・リリース間のコミット一致は各処理で確認します。

Action は GitHub の Node.js 24 ランタイムで実行します。prepare / draft と、リリース入力を省略した publish には Git、更新コマンドには Linux/macOS の Bash が必要です。公開用アセットのビルドや Docker 操作は利用側の責務です。

タグ・PR・リリース・アセットの一覧は Link ヘッダーの次ページをたどり、全件を取得します。途中のページ取得に失敗した場合は処理を停止します。

GitHub API は Octokit を使用し、リクエストごとに応答本文の読み込みを含めて30秒でタイムアウトします。変更操作を重複させないため、SDK の自動再試行とレート制限による再試行は無効にします。存在確認のみ404を未存在として扱い、他の通信・権限エラーでは停止します。API 応答の構造は Octokit の型に従い、ドラフト状態・タグ・コミット・アセットの公開条件はサービスで確認します。

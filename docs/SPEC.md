# リリース仕様

easy-release は、1 つのリポジトリに対して 1 つの安定版セマンティックバージョン（`X.Y.Z`）を管理する GitHub Action です。複数パッケージに対する個別独立したバージョン管理や、プレリリース版の管理には対応していません。

本リポジトリ自身も、自身の `Release` ワークフローによってリリースされています。手動実行（workflow_dispatch）でバージョンの更新種別を選択するとリリース準備 PR が作成され、マージ後に publish ジョブを実行することで、リリースタグと GitHub Release の作成・公開が完了します。Action の配布物は、タグに含まれる `action.yml` と `dist/index.mjs` です。

バージョン入力には、セマンティックバージョニングに厳密に準拠した表記のみを受け付けます。接頭辞 `v` の付与、前後の空白文字、先頭の余分なゼロ、プレリリース識別子（`-alpha` 等）、ビルドメタデータ（`+build` 等）を含む入力は自動補正せず、すべて不正な入力として拒否します。

## 設定

設定ファイルは JSON 形式です。全モード共通で `config` 入力（デフォルト: `.github/easy-release.json`）から読み込まれます。未定義のプロパティが含まれている場合は設定ミスとして拒否します。ファイルの不在、不正な JSON フォーマット、設定値のバリデーション失敗が発生した場合は、リリース処理の開始前に処理を中断します。

| キー                | 必須 / 既定値      | 意味                                                                                        |
| ------------------- | ------------------ | ------------------------------------------------------------------------------------------- |
| `packageFiles`      | 必須               | 更新対象ファイルを指定する glob パターンの配列（除外パターンは不可）。コマンドのみなら `[]` |
| `tagPrefix`         | `v`                | リリースタグの接頭辞。空文字 `""` も指定可能                                                |
| `updateVersionTags` | `false`            | 公開成功後にメジャー・マイナータグ（例: `v1`, `v1.2`）を両方自動更新するかどうかの真偽値    |
| `branchPrefix`      | `release/prepare-` | リリース準備ブランチの接頭辞。この末尾に完全なリリースタグ名が付加される                    |
| `updateCommand`     | 省略時は実行なし   | パッケージ更新後に実行する Bash コマンド                                                    |

ファイルパスはリポジトリルートからの相対パスとして扱います。更新対象として絶対パス、親ディレクトリの参照（`../`）、シンボリックリンク、ならびに `node_modules` や `.git` ディレクトリ内のファイルを指定することはできません。指定された条件に一致するファイルのみを更新対象とし、パスの重複は自動的に排除されます。すべての対象ファイルが有効な JSON であり、安定版の `version` フィールドを保持していることを確認したうえで書き込みを行います。パッケージファイルに既存で書かれているバージョン値は計算基準としては使われず（Git タグを基準として計算）、ファイル間でバージョンが異なっていた場合でも、すべて新しく計算された同一バージョンに統一されます。ファイルの整形においては、元のインデント幅や改行コード（LF / CRLF）を保持しますが、その他の JSON 表現は再シリアライズされます。

## バージョンの決定

GitHub API を用いてリポジトリ内のすべての Git タグを全ページ取得し、`tagPrefix` を除いたタグ名が正規の安定版セマンティックバージョン（`X.Y.Z`）であるものを抽出します。SemVer の規則に従って最大のバージョンを現在のバージョンとみなし、タグの作成日時、API から返却された順序、特定ブランチへの到達可否、GitHub Release の公開ステータスなどによる絞り込みは行いません。プレリリースやビルドメタデータが付与されたタグ、およびバージョン規則に合致しない無関係なタグは取得対象外となります。

条件に合致するタグがリポジトリ内に存在しない場合は `0.0.0` を基準とし、初回の patch / minor / major はそれぞれ `0.0.1` / `0.1.0` / `1.0.0` として計算されます。通信障害等でタグ一覧の取得に失敗した場合は、初回扱いにはせず処理をエラーとして中断します。`packageFiles: []` を指定した場合はパッケージのバージョン更新を行わず、更新コマンド（`updateCommand`）を用いて任意のファイルを更新できます。

バージョン更新後に Git の変更差分が存在しない場合であっても、ベースコミットと同一のツリーオブジェクトを参照する空コミットを作成して準備 PR を作成します。パッケージファイルがすでに更新予定のバージョンと一致している場合や、`packageFiles: []` かつ `updateCommand` 未指定の場合もこれに該当します。バージョンのバリデーションや更新コマンドの失敗条件は、変更差分の有無にかかわらず通常どおり適用されます。

## 準備 PR

Action のログ出力、エラーメッセージ、生成される PR のタイトルおよび本文、準備コミットのメッセージはすべて英語で記述されます。

PR のベースブランチは、イベントペイロードの `repository.default_branch` から取得します。`prepare` モードの実行は、このデフォルトブランチに対する手動トリガー（`workflow_dispatch`）に限定されます。実行時の条件として、checkout された HEAD コミット、ワークフロー実行時のイベント SHA、およびリモートのベースブランチの先端コミットがすべて一致し、かつワーキングツリーが clean（未コミットの変更がない状態）であることが求められます。バージョンのインクリメント計算では、SemVer の仕様に従い、major 指定時はメジャー番号を 1 増やしてマイナー・パッチを 0 にリセットし、minor 指定時はマイナー番号を 1 増やしてパッチを 0 にリセットします。patch 指定時はパッチ番号を 1 増やします。各数値は JavaScript の安全な整数範囲（`Number.isSafeInteger`）内に収まっている必要があります。

更新コマンドには、Git タグから決定された更新前バージョンが環境変数 `PREVIOUS_VERSION` として、更新後のバージョンが `RELEASE_VERSION` として渡されます。Action 側で更新コマンド固有のタイムアウトは設けていません。プロセスの異常終了、標準出力・標準エラー出力の合計サイズが上限（64 MiB）を超過した場合、またはコマンド実行によって対象パッケージのバージョンが書き戻されたり削除されたりした場合は処理失敗となります。コマンドが異常終了した際は、生成されたプロセスグループ全体を強制終了します。コマンドによって変更されたファイルは、Git のトラッキングおよび `.gitignore` のルールに従って収集されます。バイナリファイルの変更、ファイルの削除、実行権限（パーミッション）の変更は保持されますが、Git サブモジュールの変更は許可されずエラーとなります。

ブランチ名およびタグ名は、Git の参照名（ref）として有効であることを検証してからリモートへの反映を行います。GitHub 上に準備コミットを作成した後、同一リポジトリかつ同一ベースブランチを対象とするオープンな PR の中から、設定されたブランチ接頭辞およびバージョンと厳密に一致する既存の準備 PR を検索し、それらをクローズして対応するブランチを削除します。その後、新たな準備ブランチと PR を作成します。既存のリリースタグを上書きすることはありません。PR が存在しない同名ブランチがリモートに残っている場合、その先端コミットのメッセージが今回の準備コミットメッセージと完全に一致するときのみ、前回の中途状態とみなしてブランチを削除・再作成します。それ以外の原因で同名ブランチが存在する場合は処理を拒否します。設定されたブランチ接頭辞は本 Action 専用として運用されることを前提としています。一連の GitHub API 操作はアトミックなトランザクションではないため、途中でエラーが発生した場合はその時点までに実行された変更がそのまま残ります。

## ドラフトと公開

`draft` モード、および `release-id`・`tag`・`commit` をすべて省略した `publish` モードは、プルリクエストが閉じられたイベント（`pull_request: closed`）をトリガーとして実行されます。PR がマージされていること、同一リポジトリ内からの PR であること、マージ先がリポジトリのデフォルトブランチであること、PR のブランチ名が準備ブランチの命名規則に一致していることの 4 条件を満たさない PR については、リリース対象外と判定して `ready: false` を返します。条件を満たす PR の場合は、checkout されたコミットが PR のマージコミットと一致していることを確認したうえで、準備ブランチ名からリリース予定のバージョンを取得します。設定ファイルの glob パターンを再展開し、マージ時点におけるすべての対象パッケージのバージョンが予定バージョンと一致していることを検証します。このフェーズでは、Git タグからのバージョン再計算は行いません。

リリースタグはマージコミットに対して作成されます。同名のタグがすでに存在する場合は参照先コミットを確認し、異なるコミットを指している場合はエラーとなります。GitHub Release は `draft: true` かつ GitHub の自動生成リリースノートを有効にして作成されます。同じタグ・同じコミットに対応する既存のドラフトリリースがある場合はそれを再利用します。すでに公開済みのリリースが存在する場合はエラーとして処理を中断します。

アセット添付を行わないフロー（prepare → publish）では、準備 PR のマージコミットを checkout した状態で `mode: publish` を実行します。バージョン検証、checkout の確認、パッケージファイルの検証、タグおよびドラフトリリースの作成（または既存ドラフトの再利用）、公開条件の検証、そして最終的なリリース公開までを 1 回の Action 呼び出しで完結します。正常に完了した場合は `ready: true`、`version`、`tag`、`commit`、`release-id`、`release-url` を出力します。対象外の PR の場合は `ready: false` のみを出力します。処理の途中で失敗した場合は中断され、作成済みのタグやドラフトリリースはそのまま残ります。同じタグ・コミットのドラフトが存在する状態から再実行することは可能ですが、一度公開が完了したリリースを再公開することはできません。

既存のドラフトリリースを公開する場合は、`release-id`・`tag`・`commit` の 3 つをすべてパラメータとして指定します。一部のみを指定した場合は入力エラーとなり、PR イベントからの直接公開モードへ自動的に切り替わることはありません。この指定方式でも設定ファイルを読み込むためリポジトリの checkout は必要ですが、PR イベントの検証やパッケージファイルのバージョン確認はスキップされます。

リリースへのアセット添付は、ユーザー側のワークフロー内でビルドおよび添付処理を実行します。`publish` モードは、指定された ID のリリースがドラフト状態であること、タグおよび対象コミットが一致していること、添付されたすべてのアセットのアップロードステータスが `uploaded`（完了）になっていることを確認したうえで、`draft: false` かつ `make_latest: true` に更新して正式公開します。必要なアセットの種類や個数は Action 側では判定しません。同一ジョブ内で実行する場合は必要なアセット添付ステップの後に publish ステップを配置し、複数ジョブに分割する場合はアセットビルド・添付を行うすべてのジョブを `publish` ジョブの `needs` に指定してください。アセットが 0 件のリリース公開にも対応しています。

### メジャー・マイナータグ

ドラフトの利用有無にかかわらず、設定ファイルの `updateVersionTags` が `true` に設定されている場合、リリースの公開完了を確認した後にメジャー、マイナーの順でタグを更新します。たとえばバージョン `v1.2.3` を公開した場合、`v1` および `v1.2` が更新対象となり、すでにタグが存在する場合はその参照先コミットを強制更新し、存在しない場合は軽量タグとして新規作成します。既存のタグが注釈付きタグ（annotated tag）であった場合も、その参照先を今回の対象コミットへ付け替えます。完全なバージョンを表すタグ（`v1.2.3`）自体は変更しません。なお、`prepare` および `draft` モードではこのオプションによるタグ更新は行われません。

タグの接頭辞には設定ファイルの `tagPrefix` が使用されます。このオプションが有効な場合、API 呼び出しの前に、リリースタグが指定の接頭辞と正規の安定版セマンティックバージョン（`X.Y.Z`）で正しく構成されているかを検証します。たとえばタグが `app/1.2.3` かつ接頭辞が `app/` であれば `app/1` と `app/1.2` が更新され、タグが `v0.2.3` であれば `v0` と `v0.2` が更新されます。

更新されるタグは、今回公開されたリリースのコミットを直接指すようになります。既存タグが指しているバージョンの新旧比較は行わず、過去のバージョンを意図的に公開した場合でも指定のコミットへタグが移動します。メジャー・マイナータグは完全なセマンティックバージョン表記ではないため、次回の `prepare` モード実行時における現在バージョンの算出対象には含まれません。

リリースの公開処理と各タグの更新処理は、不可分なトランザクションではありません。タグの取得・作成・更新の途中でエラーが発生した場合は処理を中断し、すでに公開されたリリースや更新済みのタグはそのまま残ります。Action が自動的にリトライを行ったり、元の状態へロールバックしたりすることはありません。すでに公開済みのリリースに対して publish を再実行することは拒否されるため、失敗した未完了のタグ更新は手動で実行してください。

## 実行環境と外部通信

コミット識別子（SHA 等）の入力は空文字でない文字列として受け付け、桁数や文字種のバリデーションは行いません。PR が未マージのイベントにおいては、マージコミット SHA の `null` を許容します。checkout されたコミット、タグ、リリース間でコミットの一致確認は各処理フェーズで実施されます。

本 Action は GitHub Actions の Node.js 24 ランタイム環境で動作します。`prepare`、`draft`、および入力パラメータを省略した `publish` の実行には Git コマンドが必要です。また、`updateCommand` の実行には Linux / macOS 環境の Bash が必要です。公開用アセットのビルドや Docker 関連の操作は、Action を利用する側のワークフローで実行してください。

タグ、PR、リリース、アセットの一覧取得では、HTTP レスポンスの `Link` ヘッダーをたどってすべてのページを走査し、全件を取得します。途中のページ取得でエラーが発生した場合は処理を直ちに中断します。

GitHub API との通信には Octokit を使用し、リクエストごとにレスポンス本文の読み込み完了を含めて 30 秒のタイムアウトを設定しています。意図しない重複更新を防ぐため、Octokit SDK の自動リトライ機能およびレート制限に対する自動再試行は無効化しています。リソースの存在確認処理における HTTP 404 エラーのみ「リソース未存在」として正常にハンドリングし、その他の通信エラーや権限不足エラーが発生した場合は処理を中断します。API レスポンスのデータ構造は Octokit 提供の型定義に準拠し、ドラフト状態、タグ、コミット、アセットの公開条件などの妥当性検証はサービス層で実施します。
